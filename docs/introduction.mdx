## What it is

Amperstand is a **self-hosted personal vault**. It has two parts you need to understand:

1. **The server (`amperstand-core`)** — the only thing that touches your data. Runs on a box you control: a $4 droplet, a home NAS, even localhost. Exposes a REST API.
2. **Clients (anything that speaks HTTP to the server)** — the official CLI (`amperstand`), a Telegram bot, a Chrome extension, your own agent code. Capture surfaces, query surfaces, integration glue. The bot and extension aren't special — they're just two HTTP clients we ship as reference implementations. You can replace either of them, or add a fifth client tomorrow, and the server doesn't care.

That's the entire architecture. One server. N clients. HTTP between them.

## Architecture

```
   ┌────────────────────────────────────────────────────────────┐
   │  Clients  (any HTTP client speaking the API)               │
   │                                                            │
   │  ┌─────────┐  ┌──────────┐  ┌─────────┐  ┌──────────────┐  │
   │  │  CLI    │  │ Telegram │  │ Chrome  │  │  your agent  │  │
   │  │ amper-  │  │   bot    │  │  ext.   │  │  / script    │  │
   │  │ stand   │  │          │  │         │  │  / anything  │  │
   │  └────┬────┘  └────┬─────┘  └────┬────┘  └──────┬───────┘  │
   │       │            │              │              │         │
   └───────┼────────────┼──────────────┼──────────────┼─────────┘
           │            │              │              │
           └────────────┴──────┬───────┴──────────────┘
                               │  HTTP + API key
                               │
                       ┌───────▼──────────┐
                       │                  │
                       │  amperstand-core │   ← the server
                       │   (FastAPI)      │
                       │                  │
                       │  extractors      │   trafilatura, yt-dlp,
                       │  vault store     │   feedparser, IMAP, …
                       │  feed registry   │
                       │  job queue       │   async capture
                       │  search index    │   FTS5 + sqlite-vec
                       └────────┬─────────┘
                                │
                                │  reads & writes
                                │
                       ┌────────▼─────────┐
                       │  vault dir       │   ← markdown files on disk
                       │  .store/meta.db  │   ← SQLite index (rebuildable)
                       └──────────────────┘
```

**The server is the only process that touches the vault directory.** Clients send a URL or some content, get back JSON. They never read or write the markdown files directly.

**Clients are interchangeable.** Today we ship a CLI, a Telegram bot, and a Chrome extension. Each is ~300–600 lines of code wrapping the same six or seven HTTP endpoints. Build a Discord bot, a CLI in Go, an iOS Shortcut, an n8n flow — the server doesn't know or care.

## What it captures

| Surface | Extractor |
| --- | --- |
| Articles & blog posts | trafilatura, Playwright fallback for JS-heavy pages |
| YouTube videos | `yt-dlp` metadata + transcript API + optional Whisper fallback |
| LinkedIn posts | URL-shape extractor |
| Twitter / X | `fxtwitter` rewrite + thread reconstruction |
| RSS / Atom feeds | `feedparser` + per-item extraction |
| Newsletter emails | `.eml` parsing, IMAP fetch loop |

All extraction runs **on the server**. Clients just hand over a URL (or HTML, or an .eml file) and wait for the result.

## Why this shape

- **One vault, many clients.** Capture from your phone via Telegram, one-click from the browser, batch from a script — everything lands in the same searchable store.
- **Data sovereignty.** The vault is plain markdown files on a server you own. The tool can disappear; the files don't.
- **Stable surface.** The HTTP API is the contract. Build any client in any language. Your own agents query the same endpoints the bot does.
