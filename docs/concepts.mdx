## The vault

The vault is **a folder of markdown files plus a sidecar SQLite database**, both living on your server. Files are the source of truth; SQLite is an index you can drop and rebuild from the files alone.

Every captured doc looks like this on disk:

```markdown
---
id: 01JK8XQ4...        # ULID — sortable, URL-safe, the only stable handle
title: Why hardware development is hard
source: https://danluu.com/...
type: article
created_at: 2026-06-19T19:01:59Z
body_hash: a3f2d1...    # content hash; used to detect edits
---

# Why hardware development is hard

...markdown body...
```

The frontmatter is the canonical metadata. SQLite holds the same fields plus full-text and vector indexes for search.

The vault lives at `$AMPERSTAND_DATA_DIR` on the server (default: `/var/lib/amperstand/vault` in production). Clients never touch these files directly — they go through the HTTP API.

### Frontmatter schema (contract)

Every captured doc has these frontmatter fields. Field names and types are part of the API contract — your Dataview queries and link patterns won't silently break across releases.

| Field | Type | Who sets it | Notes |
| --- | --- | --- | --- |
| `id` | ULID (26-char string) | **Server** | Stable, sortable, URL-safe. The only handle that survives renames and re-captures. |
| `title` | string | Extractor; user may override | If you POST a `frontmatter: {"title": "..."}` to `/capture` or `/v1/docs`, your value wins. |
| `source` | URL string | Server | The URL captured. Used for idempotency (re-capturing the same URL is a no-op — see below). |
| `type` | enum: `article`, `youtube`, `linkedin`, `tweet`, `feed`, `email`, `note` | Extractor; user may override | Picked by the URL-shape detector. |
| `created_at` | RFC3339 string (always UTC `Z`) | Server | First-capture timestamp. Never recomputed on re-write. |
| `body_hash` | hex string (sha256 of the body bytes) | Server | Recomputed on every write. Detects edits and powers ETag responses. |
| `tags` | list of strings | User | Empty by default. Pass via the `frontmatter` map to `/capture` or edit in place. |
| `author` | string \| null | Extractor; user may override | Best-effort from the extractor (article byline, YouTube channel, etc.). |
| `published_at` | RFC3339 string \| null | Extractor; user may override | The original publication date when extractable (article meta tags, feed entry date). |
| `captured_at` | RFC3339 string | Server | Alias of `created_at`; both are emitted today for backward compatibility. |

User-extensible: you can add **any other key** to the frontmatter via the `frontmatter` map on `POST /capture` (or by editing the file). The server preserves unknown keys verbatim and never strips them.

<Note>
`captured_at` is an alias of `created_at` we still emit for backward compatibility with older clients. Bet on `created_at` for new Dataview queries — `captured_at` may stop being written in a future minor release. Both have identical values today; nothing breaks during the transition.
</Note>

### Slug stability (filename you query against)

The on-disk filename is the slug of the title (`why-hardware-development-is-hard.md`). The slug is deterministic for a given `id` and gets locked in at first-capture time. **Re-capturing the same URL never re-slugs the file**, even if the upstream title changes — the original filename and the original `id` are stable forever. That keeps your `[[wikilinks]]` from rotting silently.

The slugifier strips/replaces:
- Anything not `[a-z0-9-]` (so unicode titles round-trip to ASCII-ish)
- Trailing punctuation
- Whitespace runs → single `-`

Collisions (two different URLs producing the same slug from the same month) are resolved by appending `-2`, `-3`, etc. to the second/third filename.

### Extraction fidelity (what survives HTML → markdown)

| What | Behavior | Caveats |
| --- | --- | --- |
| Headings (`<h1>`–`<h6>`) | Preserved with correct level | The page's own `<h1>` is dropped (we use the frontmatter `title`) |
| Code fences | Preserved with language hint when the HTML element has a `language-foo` / `lang-foo` class | Nested fences in articles are flattened to one level |
| Inline code | `\`backticks\`` preserved | — |
| Lists (ordered + unordered) | Preserved, nesting preserved | — |
| Tables | GFM `|---|---|` syntax | Merged cells (`rowspan`/`colspan`) collapsed to first cell |
| Blockquotes | `>` preserved | — |
| Footnotes | Inline `[^1]` style preserved when source has them | Endnotes-section-only articles lose the back-link |
| Math | LaTeX `$...$` and `$$...$$` preserved when source uses them | MathJax-rendered SVGs aren't re-extracted |
| Links | Markdown `[text](url)` | Relative URLs are NOT resolved against the page's base URL today |
| Images | Markdown `![alt](url)` with the original CDN URL (hot-linked) | Images are NOT downloaded into the vault. If the source goes 404, the image dies with it. On the roadmap; not built. |
| Tweets / X embeds | Captured as a quoted snippet with the tweet URL | Thread reconstruction works for the same author; mixed-author threads sometimes miss replies |
| YouTube embeds in articles | Replaced with `[YouTube: <title>](<url>)` | Doesn't pull the transcript into the article — capture the video URL separately for that |

This isn't exhaustive — the trafilatura + custom transforms in `extractors/` handle a lot. But these are the fidelity guarantees we commit to keeping.

If you find content that breaks the contract (a code fence that loses its language, a table that mangles), it's a bug — open an issue with the source URL and we'll add a regression test.

### What happens on re-capture of the same URL?

Re-capturing a URL the vault already has is a **no-op for everything except the body**:

- The server returns the existing `doc_id` (idempotency by `source` URL).
- The body is NOT re-extracted unless the upstream content changed (detected by HTTP `ETag` / `Last-Modified` from the source, then compared against `body_hash`).
- Your user-added frontmatter fields (`tags`, custom keys, hand-edited `title`) are **preserved**. The server doesn't merge or overwrite them.

This means **edits you make in Obsidian survive re-capture**. Your PKM vault stays yours.

The only exception: if you set `force=true` on the capture request, the server treats it as a fresh capture and overwrites the body + server-controlled fields. User-added frontmatter is still preserved (server merges its fields into your existing frontmatter, doesn't replace the whole map).

### Folder layout

Captured docs land under `$AMPERSTAND_DATA_DIR/`:

```
$AMPERSTAND_DATA_DIR/
├── 2026/
│   ├── 06/
│   │   ├── why-hardware-development-is-hard.md
│   │   └── cursors-pricing-pivot.md
│   └── 07/
│       └── ...
└── .store/
    └── by-id/
        ├── 01JK8XQ4.../
        │   └── doc.md         # symlink to the year/month file
        └── ...
```

The `YYYY/MM/<slug>.md` layout is for human browsing in Obsidian / Finder / `tree`. The `.store/by-id/` tree is for the server's internal lookups (every `doc_id` resolves there).

You can't change the layout via config today. If you sync to a local Obsidian vault with its own layout convention, the [vault-sync page](/vault-sync-local) covers the rsync recipe and how to live with the year/month tree (most Dataview-driven vaults adapt fine; the alternative is forking and changing `store.py`).

## Capture surfaces

A "capture surface" is a way a URL or piece of content gets into the vault. All surfaces talk HTTP to the same server, which does the actual extraction:

| Surface | Trigger | Path |
| --- | --- | --- |
| **CLI** | `amperstand capture <url>` | POST `/capture` |
| **Telegram bot** | DM a URL to the bot | POST `/capture/async` |
| **Browser extension** | Click the extension icon on any page | POST `/capture/html/async` (sends rendered HTML) |
| **Feed sync** | Cron on the server | Server-internal (no HTTP needed) |
| **Email watch** | systemd loop polling IMAP on the server | Server-internal |
| **Your code** | POST to `/capture` from anywhere | POST `/capture` |

Notice the symmetry: every external surface uses the same REST API. The CLI and the bot and your own agent code all look identical from the server's perspective.

The async endpoints (`/capture/async`, `/capture/html/async`) return immediately with a `job_id` and run the extraction in a background worker. That exists because YouTube and long articles can take 30–120 seconds, and the Telegram bot's popup can't hang that long.

## Feed registry

Subscribed RSS/Atom feeds live in a server-side **feed registry** — a SQLite table with `feed_id`, `url`, `last_sync`, `etag`, `last_status`. The CLI's `feed add` writes to this registry via `POST /v1/feeds/register`; the server's sync job reads from it on its own schedule.

Server-side state means all clients see the same subscription list. `amperstand feed list` on your laptop and `/feeds` in the Telegram bot show the same feeds.

## Search modes

Three modes, increasing in cost and quality:

<Tabs>
  <Tab title="Keyword (FTS5)">
    Pure SQLite full-text search. Sub-millisecond, no embeddings needed. Best for exact phrases or known terminology.

    ```bash
    curl -X POST $URL/v1/docs/search \
        -H "Authorization: Bearer $KEY" \
        -d '{"q":"hardware development", "limit":10}'
    ```
  </Tab>
  <Tab title="Semantic (sqlite-vec)">
    Embedding similarity using `sqlite-vec`. Finds conceptually-related docs that don't share words. ~50ms per query. Needs `OPENAI_API_KEY` set on the server.

    ```bash
    curl -X POST $URL/v1/docs/search/semantic \
        -H "Authorization: Bearer $KEY" \
        -d '{"q":"what makes building chips slow", "limit":10}'
    ```
  </Tab>
  <Tab title="Hybrid + rerank">
    Runs both, fuses scores, then reranks top-K with an LLM. Slowest (1–3s) but best quality for "I half-remember this thing about..." queries.

    ```bash
    curl -X POST $URL/v1/docs/search/hybrid \
        -H "Authorization: Bearer $KEY" \
        -d '{"q":"that post about why chips take so long", "rerank":true}'
    ```
  </Tab>
</Tabs>

## The job queue

The async capture path writes to a `capture_jobs` SQLite table (status: `queued` → `running` → `done` / `failed`). A worker drains it with `asyncio.to_thread` + a per-job timeout. The worker is single by default; raise it with `AMPERSTAND_CAPTURE_WORKERS` if you've sized the box for it.

Inspect the queue at any time:

```bash
curl -H "Authorization: Bearer $KEY" $URL/jobs?limit=20
# { "items": [...], "queue_depth": 3 }
```

Failed jobs keep the error message and the original URL — easy to retry by hand.
