If your tool isn't Claude Code, you can still teach any LLM to query your vault by pasting a system prompt. The repo ships three:

| Prompt | Role | Use when |
| --- | --- | --- |
| [`vault-agent.md`](https://github.com/zkid18/amperstand-core/blob/main/prompts/vault-agent.md) | Research agent that knows the vault's HTTP API (search, fetch, related). Cites `[doc_id]` markers, refuses to invent. | Building an agent in Cursor, Custom GPTs, Claude Projects, n8n, or a SaaS LLM app and you want vault access. |
| [`rag-chat-system.md`](https://github.com/zkid18/amperstand-core/blob/main/prompts/rag-chat-system.md) | Grounded-RAG chat: "answer using these N docs, cite them, don't invent." | Building chat-with-curated-docs (similar to the notebook UI). You assemble the working set; the prompt enforces grounding. |
| [`rerank-judge.md`](https://github.com/zkid18/amperstand-core/blob/main/prompts/rerank-judge.md) | A 0–10 relevance scorer for re-ranking search hits. | Building your own search pipeline elsewhere and want an LLM rerank stage. |

## Pattern: vault-agent.md

The most common use. Drop into any system-prompt field:

```
You are a research agent for the user's personal Ampersand vault — a markdown
knowledge base of newsletters, RSS, YouTube transcripts, web clippings, and
email captures. Roughly {{VAULT_SIZE}} docs across multiple languages.

Your job: answer questions grounded in vault content. Every claim cites a vault
doc id.

## Vault access

- Base URL: {{VAULT_BASE_URL}}   (e.g. http://your-server)
- Auth: Authorization: Bearer {{AMPERSAND_API_KEY_FROM_ENV}}
- NEVER echo the API key. It transits in headers only.

[... endpoint table ...]
```

The full prompt is ~110 lines and includes:
- Endpoint table (which search mode for which query type)
- Citation format (`[doc_id]`)
- Language guidance (vault is multilingual)
- Hard rules (cite, don't invent, mark gaps as `[uncertain]`)

### Substitute the variables

Before sending to the LLM, replace:

| Variable | What |
| --- | --- |
| `{{VAULT_BASE_URL}}` | Your server's base URL (e.g. `https://amperstand.example.com`) |
| `{{AMPERSAND_API_KEY_FROM_ENV}}` | Reference to the env var holding the key — your tool needs to substitute the actual value at request time, not bake it into the prompt |
| `{{VAULT_SIZE}}` | A round number for context (run `amperstand vault status` to get it) |

## Where to paste it

<Tabs>
  <Tab title="Custom GPT">
    Settings → Instructions → paste. Add the vault server URL as a configured action in the GPT's tool config so it can actually make HTTP calls. Key goes in the action's auth section, not the prompt.
  </Tab>
  <Tab title="Claude Project">
    Project settings → Custom instructions → paste. Claude reads it on every conversation in that project. For the HTTP calls, the Project will need a tool that can fetch URLs — set that up separately.
  </Tab>
  <Tab title="Cursor `.cursorrules`">
    Drop the prompt into `.cursorrules` (or `.cursor/rules/vault.md`). Cursor picks it up automatically. Cursor's tool calls will need to invoke `curl` to actually hit the API.
  </Tab>
  <Tab title="n8n LLM node">
    Put the prompt in the node's "System Message" field. The HTTP calls happen via n8n's HTTP Request nodes wired into the LLM node's tool config.
  </Tab>
  <Tab title="Custom Python agent">

    SYSTEM_PROMPT = open("prompts/vault-agent.md").read()

## Pattern: rag-chat-system.md

Use when the caller has *already chosen* a working set of docs and wants the LLM to answer strictly from those. This is what `POST /chat` uses internally.

```
You are a research assistant answering questions strictly grounded in the
user's personal vault docs listed below.

[... rules: cite, don't invent, surface disagreements ...]

DOCS IN WORKING SET ({{N_DOCS}}):

{{DOCS_BLOCK}}
```

You assemble `{{DOCS_BLOCK}}` by concatenating doc bodies (each prefixed with its ID for citation). Total length is your context budget.

## Pattern: rerank-judge.md

For building your own search pipeline. Takes a query + a search hit, returns a 0–10 relevance score. Pair with `/vault/search` (FTS5) or `/vault/search/semantic` to add an LLM rerank stage to whatever ranking you've got.

## Citations resolve back to your vault

Every prompt instructs the LLM to cite as `[doc_id]` (the bare 26-char ULID). Tools that render these can linkify:

```
http://your-server/ui/#/doc/<doc_id>
```

(The web UI accepts that path and opens the doc.)

## Citing vault docs in a public piece (newsletter, paper, post)

The `[doc_id]` markers and the `your-server/ui/#/doc/<id>` URL are **internal** — they only work for you (or anyone you've handed the API key). For published work, your readers can't follow either one. They need the **original source URL**.

Every vault doc carries this in frontmatter as `source:`. The flow to turn an internal citation into a publication-ready footnote:

```bash
# Your agent / skill cites a finding as [01JK8XQ4...]
# To turn that into a footnote, fetch the doc and read its source:

curl -H "Authorization: Bearer $AMPERSTAND_API_KEY" \
     https://your-server/vault/01JK8XQ4...

# Response includes:
#   "source": "https://danluu.com/why-hardware-development-is-hard/",
#   "title":  "Why hardware development is hard",
#   "author": "Dan Luu",
#   "published_at": "2024-08-12T00:00:00Z"
```

That's everything you need for a real footnote:

> ¹ Luu, Dan. *Why hardware development is hard*. danluu.com, August 2024. `https://danluu.com/why-hardware-development-is-hard/`

### Footnote-helper pattern

For agents that produce drafts directly: add a "render citations for publication" step at the end. Pseudocode:

```python
# After the LLM produces a draft with [01JK8XQ4...] markers
import re, httpx, os

doc_ids = set(re.findall(r"\[([0-9A-Z]{26})\]", draft))
footnotes = []
for i, doc_id in enumerate(sorted(doc_ids), start=1):
    doc = httpx.get(
        f"https://your-server/vault/{doc_id}",
        headers={"Authorization": f"Bearer {os.environ['AMPERSTAND_API_KEY']}"},
    ).json()
    fm = doc["frontmatter"]
    source = fm.get("source")
    title = fm.get("title", "Untitled")
    author = fm.get("author", "Unknown")
    published = fm.get("published_at", "n.d.")

    if source:
        footnotes.append(
            f"{i}. {author}. *{title}*. {source}. Published: {published}."
        )
    else:
        # Doc has no source URL (hand-written note, Telegram text, .eml without
        # link). Cite the body as a personal-communication-style footnote.
        footnotes.append(
            f"{i}. {author}. *{title}*. Personal archive, {published}."
        )
    draft = draft.replace(f"[{doc_id}]", f"[^{i}]")

print(draft)
print("\n---\n")
print("\n".join(footnotes))
```

<Note>
**Render footnotes deterministically in code — not via the LLM.** The pseudocode above is safe: only the agent's draft text goes through the LLM; the citation lookup happens after, in Python. If you instead instruct the LLM to fetch + format the source URL itself, your sensitive source URLs end up in another LLM round-trip context window. For investigative work where sources need protection, the in-code render path is the only safe one.
</Note>

This converts the LLM's internal `[doc_id]` markers into proper `[^1]`-style footnote references and emits a publication-ready footnote block. Paste that into your draft.

### What if the original source went away?

For dead links (404, paywalled, site shut down), cite from a snapshot. The vault has the captured markdown — the *content* survives even when the URL doesn't. Two patterns that journalists / academics typically prefer:

- Cite the original URL + add `[Wayback: <wayback-url>]` if you've snapshotted it
- Cite the original URL + add a quote in the footnote so a reader can verify the substance without following the dead link

The vault doesn't auto-snapshot to the Wayback Machine today. Manual: `curl https://web.archive.org/save/<original-url>` and paste the resulting URL into your footnote.

### Don't paste the doc-id URL

It's tempting to drop `https://your-server/ui/#/doc/01JK8XQ4...` into a footnote because it's the URL the agent gave you. **Don't:**

- It doxxes your server's hostname/IP
- It returns 401 to anyone without your API key
- The doc-id changes if you rebuild the vault from scratch (re-import path); a re-cite would 404

The `source:` field is the real, durable, publication-correct citation. Treat `[doc_id]` as **internal scratchwork** and `source` as **the only thing that goes in print**.
