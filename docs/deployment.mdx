This is the operations runbook. The [Set up a server](/quickstart) page gets you a working install in 10 minutes; this page is what you reference when you need to back something up, restore from a backup, rotate a leaked key, or harden the box before exposing it.

Reference layout for the rest of this page — a 1-vCPU, 1GB DigitalOcean droplet running the server, the Telegram bot, and the IMAP email watcher.

## Layout

```
/opt/amperstand/                       ← venv + git checkout (read-only at runtime)
/etc/amperstand/env                    ← AMPERSTAND_API_KEY, IMAP creds, OpenAI key
/var/lib/amperstand/vault/             ← vault data root (set as $AMPERSTAND_DATA_DIR)
  ├── 2026/06/<slug>.md                ← markdown files (YYYY/MM tree)
  ├── .store/meta.db                   ← SQLite metadata + FTS5 index
  ├── .store/capture_jobs.db           ← async capture queue
  └── .store/by-id/<doc_id>/doc.md     ← symlinks for stable doc-id lookup
```

Owned by a dedicated `amperstand` user (no shell, no home dir).

## systemd units

The core ships these units in `deploy/systemd/`, all using the same hardening profile:

| Unit | What | Repo |
| --- | --- | --- |
| `amperstand-server.service` | FastAPI + uvicorn, listens on `:80` via Caddy | core |
| `amperstand-vault-watcher.service` | Watchdog-driven re-index of hand-edited markdown | core |
| `amperstand-feed-sync.service` + `.timer` | Periodic RSS sync (runs `amperstand-admin feeds-sync`) | core |
| `amperstand-email-watch.service` | IMAP fetch loop, persists via the server's API | core |
| `amperstand-tg-bot.service` | Telegram bot. Ships from the `amperstand-bot` repo, not core. Drop it into `/etc/systemd/system/` after cloning that repo. | bot repo |

Common hardening flags:

```ini
NoNewPrivileges=yes
ProtectSystem=strict
ProtectHome=true
PrivateTmp=true
PrivateDevices=true
ProtectKernelTunables=yes
ProtectKernelModules=yes
ProtectControlGroups=yes
ReadWritePaths=/var/lib/amperstand
```

The `ReadWritePaths` line is the load-bearing one — without it, `ProtectSystem=strict` would block writes to the vault and you'd see `sqlite3.OperationalError: attempt to write a readonly database` with no obvious explanation.

## Swap (mandatory on 512MB)

trafilatura + sqlite-vec can briefly spike past 400MB during large captures. Without swap, the kernel OOM-kills uvicorn and the server restarts.

```bash
fallocate -l 2G /swapfile
chmod 600 /swapfile
mkswap /swapfile && swapon /swapfile
echo "/swapfile none swap sw 0 0" >> /etc/fstab
```

## Caddy reverse proxy

Caddy terminates TLS (free Let's Encrypt cert) and proxies to uvicorn on `127.0.0.1:8765`. Config lives at `deploy/Caddyfile.tls` in the repo.

## Backups

A real runbook, not a one-liner. Three things to back up; one to skip; one to verify.

### What to back up

| Thing | Where | Why |
| --- | --- | --- |
| **Vault markdown** | `/var/lib/amperstand/vault/` | The actual content. Source of truth. |
| **Env file** | `/etc/amperstand/env` | API key, OpenAI key, IMAP creds, Telegram token. Re-installing without this means re-rotating every secret. |
| **Classifier model + feedback** | `/var/lib/amperstand/.classifier/` | Your trained newsletter classifier + the labeled feedback that built it. Cheap to lose, expensive to re-label. |

### What to skip

| Thing | Why |
| --- | --- |
| `.store/meta.db`, `.store/meta.db-wal`, `.store/meta.db-shm` | SQLite metadata + FTS5 index — fully reconstructible from the markdown via `amperstand-admin reindex`. Backing it up is wasted bandwidth at best, and copying mid-write can produce corrupted files. |
| `.store/capture_jobs.db*` | Async capture queue — losing it loses any in-flight queued jobs (recoverable: re-POST). |
| `.store/by-id/` (symlinks) | Internal lookup tree. Rebuilt on first server start. |

### Nightly backup (additive, off-box)

```bash
# /etc/cron.daily/amperstand-backup — runs as root
#!/usr/bin/env bash
set -e
DATE=$(date -u +%Y%m%dT%H%M%SZ)
DEST=backup-host:/backups/amperstand

# Vault markdown — additive, no --delete, so a single bad capture doesn't wipe history
rsync -az --exclude='amperstand.db*' --exclude='.store/' \
    /var/lib/amperstand/vault/ ${DEST}/vault/

# Env file (encrypted on the way out)
gpg --cipher-algo AES256 --symmetric --batch --passphrase-file /root/.backup-pass \
    -o - /etc/amperstand/env \
    | ssh ${DEST%%:*} "cat > ${DEST#*:}/env-${DATE}.gpg"

# Classifier state
rsync -az /var/lib/amperstand/.classifier/ ${DEST}/classifier/
```

The env file is encrypted before it leaves the box. Don't backup secrets in plaintext.

### Hot backup of SQLite (for paranoia)

If you DO want a point-in-time SQLite snapshot for fast restore-without-reindex:

```bash
# Atomic — uses SQLite's online backup API; safe during writes
sqlite3 /var/lib/amperstand/vault/.store/meta.db \
    ".backup /tmp/amperstand-meta-$(date +%Y%m%d).db"
```

Then rsync the resulting `.db` file. Avoid copying the live DB directly with `cp` / `rsync` — you can catch it mid-WAL-checkpoint and get an inconsistent file.

### Mid-capture rsync — is it safe?

Yes for the markdown files. The server writes via the atomic-rename pattern (`open(path.tmp); write; rename(path.tmp → path)`), so rsync either sees the old file or the new file, never half-written.

The SQLite database is a different story — see the hot-backup note above.

### Restore

From a backup-host's copy:

```bash
# On a fresh droplet, after running bootstrap.sh:
sudo systemctl stop amperstand-server

# Pull the vault back
rsync -az backup-host:/backups/amperstand/vault/ /var/lib/amperstand/vault/
chown -R amperstand:amperstand /var/lib/amperstand/

# Pull the env file (decrypt)
ssh backup-host "cat /backups/amperstand/env-latest.gpg" \
    | gpg --decrypt --batch --passphrase-file /root/.backup-pass \
    > /etc/amperstand/env
chmod 0640 /etc/amperstand/env
chown root:amperstand /etc/amperstand/env

# Rebuild the metadata + FTS5 sidecar from the markdown
sudo -u amperstand /opt/amperstand/venv/bin/amperstand-admin reindex
# (then refresh vector embeddings if you use semantic search — costs OpenAI tokens)
sudo -u amperstand /opt/amperstand/venv/bin/amperstand-admin vec-rebuild

# Bring it up
sudo systemctl start amperstand-server
curl http://localhost/health
```

Reindex time scales with vault size — roughly 1 minute per 5,000 docs on the reference droplet (single-CPU, SQLite + embedding regen if `OPENAI_API_KEY` is set). For 50k docs, plan ~10 min of "server up but search results thin."

### Retention

No built-in policy. A simple shape that works:

| Tier | Frequency | Keep |
| --- | --- | --- |
| Daily | Cron above | Last 7 |
| Weekly | Sunday's daily, promoted | Last 4 |
| Monthly | First-of-month, promoted | Last 12 |

Implement with `tmpwatch`, `restic forget --keep-daily 7 --keep-weekly 4 --keep-monthly 12`, or any object-storage lifecycle policy. The vault grows slowly (markdown compresses well), so storage cost is minor — long retention is cheap insurance.

### Integrity check

After every restore (or as a weekly cron):

```bash
# Count files and bytes; compare against pre-restore baseline
find /var/lib/amperstand/vault -type f -name '*.md' | wc -l
du -sh /var/lib/amperstand/vault

# Walk every doc, parse frontmatter, verify content_hash on disk matches
sudo -u amperstand /opt/amperstand/venv/bin/amperstand-admin integrity --deep
```

`integrity --deep` walks every `.md` file, parses its frontmatter, checks that `id` resolves through the `.store/by-id/` symlink tree, and recomputes `content_hash` from disk to compare against the value in the frontmatter. Discrepancies mean either: (a) someone hand-edited the file without going through the API (the watcher's job is to catch this and reindex; integrity reports the lag), or (b) the file is corrupted.

## Create or rotate the API key

There's a dedicated page for this: **[Create or rotate the API key](/api-key)** — covers both the laptop-side (`amperstand rotate-key`) and SSH-side (`amperstand-admin rotate-key`) paths, when to use each, and the post-rotation per-client checklist.

The short version below covers the SSH path; for the one-command laptop flow, see the page above.

To **create a new key from SSH** — either replacing a leaked key, or just refreshing on a schedule:

<Note>
**You don't need the existing API key to issue a new one.** `amperstand-admin` reads `/etc/amperstand/env` directly via filesystem perms — it bypasses the HTTP API entirely. The credential that gates rotation is **SSH access to the server** (plus sudo), not the API key itself. If you lost the current key, that's a recovery story, not a lockout.

To retrieve the current key (if you have SSH and don't want to rotate yet):
```bash
ssh root@<your-server>
grep '^AMPERSTAND_API_KEY=' /etc/amperstand/env | cut -d= -f2-
```
</Note>

```bash
# On the droplet — surgical, ownership-preserving:
sudo -u amperstand /opt/amperstand/venv/bin/amperstand-admin rotate-key \
    --env-file /etc/amperstand/env

# Restart services that read /etc/amperstand/env
sudo systemctl restart amperstand-server amperstand-vault-watcher amperstand-feed-sync.service
# Plus any client units (e.g. Telegram bot) that share the env file.

# Verify
sudo systemctl is-active amperstand-server
```

The new 64-char hex key prints to stdout once — copy it now. The command does a **targeted edit on just the `AMPERSTAND_API_KEY=` line**: comments, other secrets (`OPENAI_API_KEY`, IMAP creds), and the `0640 root:amperstand` file ownership are all preserved. The key never appears on a command line, so it doesn't leak into shell history, the sudo audit log, or `/proc/<pid>/cmdline`.

**Then update each client:**

- **CLI on your laptop**: edit `~/.amperstand-api-key` with the new value, then `source ~/.zshrc`
- **Telegram bot**: already restarted above (reads the same env file), no further action
- **Chrome extension**: paste the new key into the extension's options page on every browser running it

**Multiple keys?** There's no per-client / per-scope / read-only key concept today — `AMPERSTAND_API_KEY` is a single master credential. See [Authentication](/api-reference/authentication#why-one-shared-key) for the workarounds (separate servers per trust domain, reverse-proxy auth).

<Warning>
**The server drains in-flight requests for up to ~25s** after `systemctl restart`. Requests holding the old key keep succeeding during that window. For a hot leak (you saw the key in someone else's terminal), follow the restart with `sudo systemctl kill --signal=SIGKILL amperstand-server` once the new worker is up to cut the drain window to zero.

For full threat model, secure storage on each client type, and what to do if the key has leaked, see [Authentication](/api-reference/authentication).
</Warning>

For all the other admin commands (reindex, vec-rebuild, backup, integrity, classifier), see [Admin CLI](/admin-cli).
