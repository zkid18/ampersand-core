---
title: Wire the vault through a credentials gateway
description: "For agents that route HTTP traffic through a secrets gateway (BONO, etc.) that injects auth headers at the network layer instead of handing keys to the agent."
---

Some agent platforms inject credentials at the network layer rather than handing them to the agent process. The agent's `bash` / `fetch` tool calls `https://your-server/v1/...`; the gateway sees the destination, looks up the secret bound to that host, and adds the `Authorization` header before the request leaves the network. The agent's container never holds the key.

This page is the fill-in-the-blanks for plugging an Amperstand vault into that pattern.

## What you need (three things)

Copy this table and fill in your values. The gateway provisioning command at the bottom uses them verbatim.

| Field | Value for Amperstand | Example |
| --- | --- | --- |
| **API host / domain** | Your server's public hostname (no protocol, no path). | `vault.your-domain.com` (or `68.183.29.223` if you run on a bare IP) |
| **Auth method — header + format** | Amperstand uses HTTP `Authorization: Bearer <key>`. The literal token is the 64-char hex value of `AMPERSTAND_API_KEY`. | `Authorization: Bearer {value}` |
| **The key / token** | Your server's `AMPERSTAND_API_KEY`. Retrieve via SSH (you don't need to paste it anywhere outside the gateway). | `ssh root@<your-server> grep '^AMPERSTAND_API_KEY=' /etc/amperstand/env \| cut -d= -f2-` |

## Example provisioning command

This is the shape of the command for a BONO-style gateway (`onecli`). Replace `<KEY>` and the host with your actual values, then run on whatever box hosts the gateway:

```bash
onecli secrets create \
    --name "Amperstand" \
    --type generic \
    --value "<KEY>" \
    --host-pattern "vault.your-domain.com" \
    --header-name "Authorization" \
    --value-format "Bearer {value}"

# Grant it to your agent (gateway-specific — for BONO: explicit assignment,
# `--mode all` won't auto-pick it up)
onecli secrets grant Amperstand --agent BONO

# Flush the gateway and the agent can now hit the API
docker restart onecli
```

For non-BONO gateways (Vault agent, AWS Secrets Manager + Envoy, your own sidecar), the three table values feed the same conceptual slots — they just have different config syntax.

## How will the agent actually call the API?

Two options, by whether you want the agent to think in HTTP or in MCP:

| Pattern | When to use | What the agent does |
| --- | --- | --- |
| **Plain HTTP via the agent's bash/fetch tool** | Default. Works today. No extra moving parts on the Amperstand side. | `curl https://vault.your-domain.com/vault/search/hybrid -d '{"q":"..."}'` — the gateway injects the Authorization header en route. |
| **MCP server** | When the host (Claude Desktop, Cursor, etc.) speaks MCP and you want the vault as a native tool surface. | **Not built today.** On the roadmap — see [issue tracker](https://github.com/zkid18/ampersand-core/issues). For now use the system-prompt + HTTP pattern via [Vault-aware system prompt](/agent-prompt). |

## Why use a gateway at all?

The default for agent integrations is: the agent process reads `AMPERSTAND_API_KEY` from its env and sends it in every request. That's fine for personal use where you control the agent host.

Cases where the gateway shape is better:

- **Multi-tenant agent platform** — many agents share a runtime; you don't want the API key in any single agent's env (other tenants on the same host could read `/proc/<pid>/environ` depending on the isolation model).
- **Audit + revocation at the network layer** — gateway logs every outbound call; you revoke the agent by ungranting the secret without touching agent code.
- **Per-agent key scoping** — if your gateway issues per-grant tokens (Amperstand has only one master key today, but a future per-key-scope feature would integrate cleanly here).
- **Compliance posture** — "the agent never sees credentials" is sometimes a checkbox requirement.

For single-operator personal use, the simpler patterns ([Shell-out](/agent-shell) or [System prompt](/agent-prompt)) are usually enough. Reach for a gateway when one of the above applies.

## Test it works

From your agent (with the gateway injecting credentials):

```bash
curl https://vault.your-domain.com/health
# {"status":"ok"}

curl https://vault.your-domain.com/vault?limit=1
# Should NOT 401 — the gateway injected your Authorization header.
```

If you get `401 invalid api key`, the gateway either didn't inject the header or injected the wrong value. Check:

1. Gateway's host pattern matches your server's domain (no protocol, no port unless non-standard)
2. The secret value matches `AMPERSTAND_API_KEY` exactly (64 hex chars, no trailing newline — beware `echo` vs `printf` or `tr -d '\n'`)
3. Header name is exactly `Authorization` (capital A; some gateways are case-sensitive)
4. Value format wraps as `Bearer {value}` (literal word "Bearer", a space, then the placeholder)

## Rotation under this model

When you [rotate the API key](/api-key), update the gateway's secret store with the new value. The Amperstand server itself doesn't care which gateway you use — it just sees an `Authorization: Bearer <hex>` header and validates against its `AMPERSTAND_API_KEY`. The "where does the key come from" lives entirely on the agent side.
